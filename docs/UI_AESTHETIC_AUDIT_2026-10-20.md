# 欧包音乐 · 美学设计缺陷审查

> 审查对象：Stage v4「舞台」/ Aether Flow 视觉体系
> 审查时间：2026-10-20
> 运行态：默认窗口 1220 × 780，浅色与深色；另参考 1040 × 680、1600 宽、搜索下拉、播放队列、登录弹窗、歌词页
> 方法：运行态截图 + CDP 实测几何/计算样式 + tokens/CSS 统计 + WCAG 对比度计算
> 状态：**本文第 0–10 节为 2026-10-20 修复前的基线记录；修复已完成，结果见第 11 节「修复结果」。**

---

## 0. TL;DR

**核心判断：这套 UI 的问题不是"设计得不够"，而是"设计得太多、层级太少"。**

- 视觉语言本身成立：悬浮外壳、封面驱动的环境光、圆角玻璃、歌词转场都有辨识度。
- 但强调色、渐变、玻璃、光晕、投影、入场模糊被同时用在几乎所有组件上，结果是"每个东西都在喊"；真正该被看见的信息被压到 10–13px、2.0–3.5:1 的对比里。
- 首屏效率低：默认 1220 × 780 下 Hero 占 409px（视口高度 52%），歌曲表只露出 **1 行完整歌曲**，第 2 行被播放坞压住。
- 材质成本高、收益低：样式文件中 50 处 `backdrop-filter`（含 `-webkit-`）、97 处 `box-shadow`、35 处 `gradient()`、46 处 `blur()`；当前详情页仍有 19 个 `backdrop-filter` 节点（含隐藏抽屉/弹窗）。
- 语义色冲突：`--accent-primary` 与 `--color-danger` 是同一个颜色；焦点环、音质徽章、主按钮、播放指示全用这个红色系，导致"错误 / 警告 / 品牌 / 焦点"无法区分。
- 排版缺一层"中间字阶"：实际渲染中 13px（390 个文本节点）和 12px（351 个）占绝对主导，10px 仍在承担表头/分组标题；标题却跳到 43.92px / 800 字重。15–21px 的中间层几乎没被使用。

**如果只做三件事：**

1. 把强调色从"到处用"收回到"一个页面一个主色、一个主 CTA"；把 danger 从品牌色里拆出来，焦点环改成中性高对比色。
2. 做一次真正的排版与对比度整改：正文 14px、次要信息 12px、最小 11px；12–13px 文本最低 4.5:1。
3. 把 Hero 从 409px 压到 280–290px，默认窗口首屏至少完整露出 4 行歌曲；标题加 `text-wrap: balance`。

## 2. 问题一：强调色通胀与语义冲突（P0）

### 症状

同一个"粉 → 紫"渐变和同一个红色系，同时出现在：

- 侧边栏激活项（`--accent-gradient` + 12/30px 粉红光晕）；
- 顶栏"登录"按钮；
- Hero 主 CTA「播放全部 / 立即播放」；
- 歌单广场筛选激活 pill；
- 播放坞播放键（54px 渐变圆 + 大光晕）；
- 音质徽章「标准」（红字 + 红描边 + 浅红底）；
- 搜索框聚焦态（红色描边 + 4px 红光）；
- 全局 focus ring（`0 0 0 2.5px var(--accent-glow)`）；
- 正在播放的歌曲行左侧指示条；
- 歌词逐字填充色。

在一个页面里，导航、登录、播放、筛选、焦点、音质、当前播放全部在发红光。**强调没有了对比对象，就不再是强调。**

更严重的是语义冲突：

```css
/* tokens.css */
--accent-primary: #fb3b60;
--color-danger: #fb3b60;

[data-theme='light'] {
  --accent-primary: #e11d48;
  --color-danger: #e11d48;
}
```

品牌主色与危险色完全同值。结果是：

- 搜索框聚焦看起来像报错；
- 音质「标准」看起来像破坏性操作；
- 真正的错误 Toast / 危险按钮没有独立色相可用；
- 歌词的卡拉 OK 填充也用了 danger 色。

### 证据

- `screenshots/2026-10-20-aesthetic-audit-detail-light.png`：顶栏登录、Hero CTA、音质徽章三处同时发光。
- `screenshots/2026-10-20-fix-b-search-dropdown.png`：搜索聚焦的红色光圈，是全屏最像"错误状态"的元素。
- `screenshots/2026-10-20-final-home-dark.png`：侧栏激活 pill 的粉紫光晕、播放键渐变、登录按钮形成三个竞争焦点。
- 代码：`src/renderer/styles/tokens.css` 193、211、256、307、324 行；`src/renderer/styles/components.css` 309–314、708–714、1397–1408 行。

### 建议

- 拆分语义：品牌色只负责"选中 / 播放 / 品牌"；危险色单独取一个与品牌粉区分明显的红（并拉开明暗），不要和品牌同值。
- 焦点环改成中性高对比色（白/黑描边 + 外发光），不要用红色 glow；搜索聚焦只保留 1px 边框 + 1px 外环。
- 音质徽章改中性 chip（灰底、深字），文本 "标准" 本身不需要红色。
- 每个视图最多 **1 个渐变实底 CTA**；其余按钮用描边/文字层级。
- 侧栏激活项保留渐变可以，但去掉大光晕（`box-shadow` 降到 0 8px 18px rgba(...,.18)），让它回到"导航状态"而不是"广告按钮"。

## 3. 问题二：排版与对比度（P0）

### 3.1 字阶断档

设计令牌声称 10 / 11 / 12 / 13 / 14 / 15 / 17 / 21 / 34 / 46 的完整阶梯，但实际页面：

- 12–14px 占 873 个文本叶子（390 + 351 + 132）；
- 15 / 16 / 17 / 21px 合计不到 10 个；
- 10px 仍用于表头、分组标题；
- 标题跳到 43.92px / 800。

这形成了"极小 + 极大"的两极结构，中间没有舒适的阅读层。界面看起来像把杂志标题贴在一个 12px 的表格工具上。

### 3.2 对比度不合格

| 位置 | 计算样式 | 对比度 | 判定 |
| --- | --- | --- | --- |
| 歌曲表头（浅色） | 10px，`rgba(18,20,29,0.32)` | **2.07:1** | 严重不合格 |
| 歌曲序号（浅色） | 13px，同上 | **2.07:1** | 严重不合格 |
| 分组标题「发现音乐 / 我的歌单」（浅色） | 10px，同上 | **2.07:1** | 严重不合格 |
| 侧栏空态「暂无歌单」（浅色） | 12px，同上 | **2.07:1** | 严重不合格 |
| Hero 简介（浅色） | 13px，`text-tertiary` 0.5 | **3.04–3.46:1** | 不合格 |
| 登录弹窗脚注（浅色） | 12px，`text-muted` 0.32 | **2.07:1** | 严重不合格 |
| 音质徽章「标准」（浅色） | 12px，红字 / 浅红底 | 约 **4.0:1** | 不合格 |
| 歌曲表头（深色） | 10px，`rgba(245,246,251,0.34)` | **2.85:1** | 不合格 |
| 歌曲序号（深色） | 13px，同上 | **2.85:1** | 不合格 |

10px 的中文在 Windows 上本身就已经很吃力，再叠加 2:1 的灰，实际效果是"看不见但占着位置"。

### 3.3 中英混排与字重

- `--font-family` 以 `Segoe UI Variable Text` 开头，中文回退 `Microsoft YaHei UI`；同一行里英文与中文来自两套字体，x-height、字重、字面率不一致。`欧美R&B｜“顶级旋律 开口沦陷”` 是最明显的例子。
- Hero 使用 `font-weight: 800`，而常见中文字体只有 700；800 基本是浏览器合成粗体，笔画容易糊。
- CJK 标题仍套用 `letter-spacing: -0.025em`，对中文方块字是负优化。
- 没有随包 CJK 字体，跨机器一致性不可控。

### 3.4 标题孤行

在默认 1220 宽度下，Hero 标题的结果是：

- 第 1 行：`欧美R&B｜“顶级旋律 开口沦`
- 第 2 行：`陷”`

一个两字词被拆开，第二行只剩 2 个字形（含引号），视觉上像一个 bug。原因不是字号太大，而是：

- `.hero-copy` 宽度 583px；
- 标题 `clamp(30px, 3.6vw, 46px)` 在 1220 窗宽取到 43.92px；
- 没有 `text-wrap: balance` / `text-wrap: pretty`，完全交给默认断行。

换到 1100 宽时断行结果又变成 `开口 / 沦陷”`，说明它完全依赖容器宽度，没有排版约束。

### 3.5 其它排版细节

- 「展开简介」被渲染成一个独立的 48 × 28px 红色下划线链接，夹在简介和统计 chips 之间，像一条游离的注释；它应该贴着简介末尾或做成 inline 的"展开"。
- 歌曲表头用 `letter-spacing: 0.12em` + `text-transform: uppercase`，对中文只起到"把两个字拆开"的作用，10px 下更显松散。
- 时间、序号等宽数字做得不错，这是少数该保留的细节。

### 建议

- 重定字阶：`11 / 12 / 14 / 16 / 20 / 28 / 40` 七级即可；正文 14，次要 12，最小 11。10px 只允许用于真正的装饰性 eyebrow，不允许承载表头/分组结构。
- `--text-muted` 提升到深色 ≥0.62、浅色 ≥0.55（对应约 4.5:1）；把现在的 0.32 改名为 `--text-decorative`，禁止用于信息文本。
- 表格表头 11px / 600 / `text-secondary`；序号 12px / `text-tertiary`。
- 引入一套可变 CJK（如 MiSans / HarmonyOS Sans / Source Han Sans），中文用 600–700，不靠 800。
- Hero 标题加 `text-wrap: balance`，并把 `letter-spacing` 改成 0（中文）或 `-0.01em`。
- 对"欧美R&B｜"这类中英混排标题，单独定义 `font-feature-settings` 与间距，避免 `｜` 与拉丁字母挤在一起。

## 4. 问题三：首屏被 Hero 吃掉（P0）

### 症状

默认窗口 1220 × 780：

- Hero：y=76 → 485，**409px**；
- 歌曲表：y=517 开始；
- 表头 528–565，行 1 571–631，行 2 631–691；
- 播放坞从 y=680 开始，直接把行 2 的底部压住。

也就是说，打开一个 97 首歌的歌单，**首屏只能完整看到 1 首歌**。用户必须滚动才能确认"这个歌单里有什么"。

Hero 的设计目标是"广告牌"，但它现在承担了：

- 封面（150px）；
- kicker；
- 2 行 44px 标题；
- 2 行简介；
- 独立"展开简介"；
- 3 个统计 chips；
- 2 个 46px CTA。

在 780 高度里，这是不可持续的。

### 截图

- `screenshots/2026-10-20-aesthetic-audit-annotated.png`：① 标注了 Hero 409px / 52% 视口 / 首屏 1 行。
- `screenshots/2026-10-20-final-detail-dark.png`：深色下同样只有 2 行左右可见。
- `screenshots/2026-10-20-fix-b-table-1100.png`：1100 × 820 下首屏约 2.5 行，说明空间不是完全不够，而是 1220 × 780 的组合被 Hero 占满。

### 其它同源问题

- `.hero-watermark` 用 `title.slice(0, 2)` 生成"幽灵字"，字号 `clamp(150px, 20vw, 290px)`，从右侧压进正文区域；它会和简介、chips 的右缘重叠，在浅色主题下尤其像渲染残影。
- Hero 的 `.hero-backdrop`、全局 `.app-ambient`、播放坞的 `::before`、歌词页的 glow orb 是四套独立的环境光，互不同步。首页是橙色 Hero + 粉紫侧栏 + 红蓝极光，详情页是青红 Hero + 粉紫极光，颜色场一直处于"打架"状态。
- 首页 Hero 的语义也不稳定：标题是"一首推荐歌曲"，CTA 是"播放全部 12 首推荐"，统计 chip 又是"12 首推荐"。它到底是歌曲广告还是歌单广告？同一个组件在首页和详情页承担两种语义。

### 建议

- 默认窗口 Hero 上限 290px：标题 1–2 行、简介 2 行且"展开"inline、chips 与 CTA 合并到一行；封面 132–150px。
- 在 780 高度下，Hero + 表格头 + 至少 4 行必须放进首屏（可用 `clamp()` 按 `100vh` 计算，而不是固定值）。
- 删除 ghost watermark，或把它移到封面后方、降低到 3% 且不与文本列相交。
- 首页 Hero 要么改成"每日推荐歌单"的语义（标题 = 歌单名），要么改成单曲 Hero（CTA = 播放这首歌），不要混用。
- 统一环境光来源：全局环境光跟随当前播放；Hero 只保留封面本身的模糊，不再叠加第二套"极光"。

## 5. 问题四：边缘系统与空间分配（P1）

### 5.1 四条右边界

| 元素 | 右边界 |
| --- | --- |
| 内容卡片（Hero / 表格） | 1169 |
| 顶栏右侧（窗口控制） | 1202 |
| 播放坞 | 1206 |
| 原生滚动条 | 1220（宽 17px） |

设计文档写的是"没有任何元素贴边，一切都是悬浮卡片"，但实际：

- `.main-content` 是 `right: 0` + `padding-right: 34px` + `scrollbar-gutter: stable`；
- Windows 11 的 Fluent 滚动条忽略 `::-webkit-scrollbar` 的 12px 规则，实际是 17px，直接贴在窗口最右侧；
- 播放坞又比内容宽 37px，比顶栏宽 4px。

所以右缘同时存在 4 条不同的"对齐线"，而最外侧的那条正好是唯一没有设计过的原生滚动条。它是全 App 最破坏"悬浮卡片"隐喻的元素。

### 5.2 侧边栏的 115px 死区

侧栏 258 × 608：

- 空态虚线框 407–454；
- 454–569 是 **115px 纯空白**；
- 569 才开始底部登录 CTA。

`我的歌单` 是一个 228 × 37 的 sticky 标题，背景直接取 `--glass-rail`（浅色 `rgba(255,255,255,0.72)`），没有圆角，形成一条横贯侧栏的白色"纸条"；下面再放一个 47px 高的虚线框。空态和死区加起来 162px，让侧栏看起来像没有加载完。

侧栏底部又有一个登录 CTA，顶栏还有登录按钮——同一页面出现两个登录入口，且都使用渐变。

### 5.3 播放坞右侧 344px 空场

`.playerbar` 是 `1fr / 640px / 1fr` 网格：

- 左：封面 + 歌名 + 歌手；
- 中：播放控制 + 进度条；
- 右：音质 + 队列（约 100px）。

在 1220 宽度下，中间列固定 640px，但控制组实际只占约 300px；右侧 1fr 又只放音质和队列两个小按钮。两者叠加，从音量键到「标准」之间空出约 344px。视觉上播放坞像一条没铺满的横幅，同时真正的控制（音量/歌词入口）被挤在中间。

### 5.4 表格缺少 sticky header

97 行、5888px 高的表格，表头不 sticky。往下滚动后，用户失去"这是哪一列"的锚点；而表头本身只有 2.07:1 的对比，滚走也不会有损失感——但这恰恰是问题。

### 5.5 空态与加载

- 侧栏空态是一个纯虚线框，没有图标、没有行动说明；
- 主内容区在数据未到达时可能出现整块黑色空白（`2026-10-20-fix-c-a11y-focus.png` 中可见），首屏缺少一个与设计语言一致的骨架/空态；
- `[data-reveal]` 默认 `opacity: 0; transform: translateY(30px); filter: blur(12px)`，依赖 IntersectionObserver 才显示。只要 JS/观察器时序出问题，整段内容就是不可见的。这个"默认不可见"的入场策略风险偏高。

### 建议

- 统一右缘：内容、顶栏、坞、滚动条使用同一个 12–14px 外缘节奏；把滚动条改成 overlay 自定义指示器，或给 `.main-content` 增加 14px 的右侧 gutter 让滚动条落在卡片之外。
- 播放坞改 2 列或 3 列自适应，右侧补上音量滑杆 + 歌词入口，把 344px 空场变成功能。
- 侧栏空态改成一行紧凑的"暂无歌单"说明（不画大虚线框），或把空态与登录 CTA 合并成一张卡。
- 表格 header 做 sticky，背景与表格卡一致，滚动时保留列名。
- `[data-reveal]` 的初始态改为 `opacity: 1` + 只做 transform/opacity 的轻量入场；不要让内容默认不可见。

## 6. 问题五：材质与光（P1）

### 6.1 数字

- 样式文件：**50** 处 `backdrop-filter`（含 `-webkit-`）、**97** 处 `box-shadow`、**35** 处 `gradient()`、**46** 处 `blur()`。
- 当前详情页：**19** 个节点带 `backdrop-filter`（含隐藏的抽屉和弹窗）。
- 玻璃参数：sidebar/dock 48px + 200% 饱和，topbar 34px，modal 28px，aurora 100px，artwork 120px，lyrics 72px。
- 投影：`--shadow-dock: 0 26px 70px rgba(0,0,0,.62)`、`--shadow-float: 0 40px 100px rgba(0,0,0,.6)`。

### 6.2 深色下不可见，浅色下糊成一片

- 深色主题背景接近 `#05060b`，黑色大投影的视觉回报几乎为零；所谓"离地感"主要靠 1px 白色描边。
- 浅色主题中，白色半透明表面 + 彩色极光 + 28px 以上模糊，最终是一片"粉彩糊"。`2026-10-20-aesthetic-audit-detail-light.png` 的 Hero 和背景已经很难分辨层级。
- 登录弹窗把整个应用 `blur(28px)` + `scrim 0.4`，背景变成无法辨认的色块（`2026-10-20-aesthetic-audit-login-light.png`）。用户失去了"我在哪个页面"的空间上下文。

### 6.3 装饰压过内容

- Hero 的 ghost watermark 压到简介和 chips 的右缘；
- 登录二维码外圈是 7px 粉红光环 + 大阴影 + 扫描线动画，二维码本身的识别区反而被装饰包围（`login-qr-frame`，components.css 2408–2421）；
- 歌词页的 glow orb 用 `blur(90px)` + `screen` 混合，把整页变成红紫雾；
- 弹窗顶部的粉色径向光晕（`.modal-card::before`）与二维码光环、主按钮光晕、侧栏光晕叠加。

### 建议

- 把玻璃表面收敛到 **3–4 个**：侧栏、播放坞、弹窗、顶栏胶囊。列表卡、Hero、表格改成实色/低透明 surface，不再 `backdrop-filter`。
- 遮罩改用 8–12px 模糊 + 更高的纯色 scrim；保持背景可辨认，只做"退后"处理。
- 每个页面只允许一个"发光体"（播放键或主 CTA），其余发光全部删除。
- 删除大面积 `filter: blur()` 入场（尤其 5888px 的表格），改用 opacity/translate；`will-change` 只在动画期间使用。
- 定义 light/dark 两套 elevation，而不是把深色阴影直接套到浅色。

## 7. 问题六：歌词页（P1）

### 症状

- 基础行 26px、`opacity: 0.3`、颜色 `--lyrics-text-inactive`（深色 alpha 0.32，等效约 0.10）；near-1 再叠 `blur(1px)`，far-1 `blur(3px) / 0.42`，far-2 `blur(4px) / 0.25`。最终整页只有 1 行能读，其它行既看不清也无法"预习"下一句。
- 当前行 37px / 700 / `translateX(12px)` / `scale(1.02)`，在视觉上不等于"歌词高亮"，更像一个被选中的列表项。
- 浅色主题的当前行用白色 text-shadow，在浅底上形成一圈白色描边。
- 歌词页是唯一不使用悬浮外壳语言的全屏页：左侧 300px 封面（在左列中居中）+ 右侧约 514px 文本，中间留出大片空隙；页面上方/下方各有大片空白，整体重心偏下。
- 空闲时 chrome 完全隐藏（`opacity: 0` + `pointer-events: none`），页面上没有任何可见的关闭/返回入口。第一眼看上去像"卡在全屏页"。
- 当歌曲没有逐句歌词、只有 credits 行时（如 `Let It Go` 的 Lyricist / Composer），页面会把它们当作普通歌词渲染：淡、糊、且占据视觉中心，无法区分"正在加载""没有歌词""只有版权信息"。

### 证据

- `screenshots/2026-10-20-aesthetic-audit-lyrics-light.png`（当前浅色歌词页，正文几乎不可读，右侧只有 credits）
- `screenshots/2026-10-20-final-lyrics-dark.png`（深色，仅当前行清晰，其余为 blur）

### 建议

- 当前行用字号/字重/颜色建立层级，不要只靠"变成 37px + 位移 12px"；下一次高亮至少保持 0.55 的对比度，远处行不要 blur 超过 1px。
- 翻译行与原文保持固定行距，不要让 15px 翻译在 26px 原文下"失焦"。
- 增加一个明确的"无歌词/纯音乐/credits"状态卡，与正常歌词区分。
- chrome 隐藏时保留一个 32px 的低透明度关闭键或 3 秒后淡到 0.35，而不是完全消失。
- 两列改为 `minmax(240px, .8fr) minmax(0, 1.2fr)`，并在 < 1100 时单列化；不要固定 300px 封面。

## 8. 问题七：控件与微交互一致性（P2）

- 顶栏登录 = 渐变胶囊里一个粉色圆 + "登" 字 + "登录"文字；DOM 文本实际是 **"登登录"**。在 1040 宽度下文字被隐藏，只剩一个像用户头像的渐变圆——它到底是"登录"还是"已登录"？
- 音质「标准」是 50 × 30 的 9px 圆角方块，而周围所有操作都是 9999px 胶囊；它既不在形状系统里，又用 danger 色。
- 窗口控制按钮 34 × 34，图标 12–13px（最小化/最大化/关闭），与 38px 的顶栏图标、40px 的搜索/用户徽章不成比例。
- 图标线宽不统一：历史按钮 16px / stroke 2.1，窗口控制 12–13px / stroke 2，播放控制有的 filled、有的 outline。
- 所有卡片 hover 上浮 7–8px、缩放 1.06–1.10、按下 0.92–0.98；44 处 `scale()`、22 组 keyframes。一个桌面音乐播放器不应该每个像素都在动。
- 图标的语义也有错位："打开手机 App 扫一扫"旁边放的是放大镜（搜索）图标；播放坞封面上的 `Maximize2` 用来表示"打开歌词"，但视觉上像全屏。
- 浅色主题的 sticky 分组标题是直角白色条（见 5.2），深色主题下则是深色条；同一组件在两个主题里像两种东西。

### 建议

- 统一控件半径：胶囊只给"可切换项/标签/主按钮"，方形 chip 统一 10–12px；音质徽章改为中性文字 chip。
- 登录态用一个明确的用户头像 + 昵称；未登录用文字按钮"登录"，不要复用头像形态。
- 统一图标库与线宽（lucide 1.75/2 两档即可），播放控制固定 filled，其余固定 outline。
- 动效预算：每个页面只保留 1 个入场 + 1 个 hover 层级；把 44 处 scale 收敛到 8–10 处有意义的反馈。
- 小窗口（< 1100）先保证信息完整，再隐藏装饰：隐藏的是光晕/水印，不是登录文字或表头。

## 9. 值得保留的部分

这不是一次"推倒重来"的审查。以下选择是成立的，应该保留并强化：

1. **悬浮外壳几何**：14px inset、26px 圆角、侧栏/播放坞/内容三段式，在 1220 下空间关系清楚。
2. **封面驱动的环境光**：`App.tsx` 用封面取色写入 `--aurora-a/b`，思路正确；问题只是"光太多"，不是"不该有光"。
3. **歌词页的全屏转场**：封面到歌词页的 shared-element 直觉很好，只是落地时被过度模糊和过大字号拖累。
4. **`data-reduce-effects` 降级体系**：已有完整的 reduced-motion 分支，说明系统层是考虑过的；应该把它作为默认体验的一部分，而不是可选开关。
5. **`CoverImage` 的回退、骨架屏、空态基础设施**：比大多数同类项目完整。
6. **数字等宽、时间列对齐、行高锁定**：这些是真正让界面"稳"的细节。

- **歌词页布局**：当前仍是左右分栏的沉浸页；若希望更接近 Apple Music 的"单列居中 + 背景封面"模式，可作为下一轮视觉迭代。
- **媒体卡/货架在 780 高度下的首屏**：新歌速递的歌手名现在刚好贴播放坞上沿；不同 DPI/字体下可能相差 1–2px，必要时可把区块间距再收紧 2px。
